# 五金店管理系统云数据库备份实施方案

## 一、文档目标

本文档用于把“本地主库 + 云端灾备库”的方案细化成可执行实施清单和脚本设计。

本文档解决的问题：

- 先做哪些事
- 每一步的输入输出是什么
- 需要哪些脚本
- 脚本之间如何衔接
- 如何验证备份真的可恢复

本文档是后续开发备份脚本、恢复脚本和定时任务的直接依据。

当前仓库中的第一版脚本实现已放置在：

- `springboot-demo/scripts/backup`

当前提供的配置模板为：

- `springboot-demo/scripts/backup/backup.config.example.json`

## 二、实施范围

本轮只覆盖云备份落地准备，不直接改业务代码逻辑。

涉及目录建议如下：

- 文档目录：`docs`
- 后端目录：`springboot-demo`
- 后续脚本目录建议新增：`springboot-demo/scripts/backup`
- 备份输出目录建议新增：`springboot-demo/target/backups`

## 三、目标架构

建议采用标准方案：

1. 本地 MySQL 继续作为业务主库
2. 云端 MySQL 作为异地灾备库
3. 每日生成一次全量备份文件
4. 每小时归档一次增量日志或增量快照
5. 备份文件先落本地，再上传云端
6. 恢复时优先使用“最近全量 + 最近增量”

## 四、实施清单

### 4.1 第一步：明确边界和参数

目标：

- 把备份脚本需要的配置一次性定义清楚

需要确认的参数：

- 本地数据库地址
- 本地数据库端口
- 本地数据库名
- 备份账号
- 本地备份目录
- 云端备份目录或对象存储路径
- 云数据库地址
- 云数据库端口
- 云数据库名
- 云端上传账号或访问密钥
- 备份保留天数
- 全量备份执行时间
- 增量备份执行频率

本步产出：

- 参数表
- 命名规则
- 目录规则

### 4.2 第二步：准备本地备份目录

目标：

- 统一备份文件输出位置

建议目录结构：

```text
springboot-demo/
  target/
    backups/
      full/
      incremental/
      restore/
      logs/
      manifest/
```

目录说明：

- `full`：保存全量 SQL 备份
- `incremental`：保存增量日志或 binlog 归档
- `restore`：保存恢复演练时的中间文件
- `logs`：保存脚本执行日志
- `manifest`：保存每次备份的元数据清单

### 4.3 第三步：准备云端灾备资源

目标：

- 让本地备份有明确的云端落点

云端资源至少包含：

- 一台云 MySQL 实例或托管云数据库
- 一块云端备份存储空间
- 一个专用备份账号
- 允许访问的白名单规则

建议规则：

- 业务账号和备份账号分离
- 备份账号仅有备份和恢复所需最小权限
- 云端 MySQL 不直接对公网完全开放

### 4.4 第四步：实现全量备份链路

目标：

- 每天能稳定产出一份完整可恢复的 SQL 备份

本步需要完成：

1. 本地导出 SQL
2. 计算文件校验值
3. 生成 manifest 文件
4. 压缩备份
5. 上传到云端
6. 记录执行日志

### 4.5 第五步：实现增量归档链路

目标：

- 把数据丢失窗口压缩到 1 小时以内

本步需要完成：

1. 识别本次新增 binlog 或增量文件
2. 打包增量文件
3. 生成增量 manifest
4. 上传到云端
5. 记录执行结果

当前如果暂时不启用 binlog，也可先用“高频全量快照”作为过渡方案。

### 4.6 第六步：实现恢复演练链路

目标：

- 证明云端备份不是“存了就算完成”，而是真的能恢复

本步需要完成：

1. 从云端下载一份全量备份
2. 恢复到隔离数据库
3. 校验核心表数量
4. 校验核心业务链路
5. 输出恢复报告

### 4.7 第七步：接入定时任务和告警

目标：

- 让备份变成持续运行能力

本步需要完成：

1. 配置每日全量任务
2. 配置每小时增量任务
3. 配置失败告警
4. 配置保留策略清理任务

## 五、脚本设计

建议脚本按职责拆开，不要把所有逻辑塞进一个脚本。

### 5.1 脚本清单

建议新增以下脚本：

- `springboot-demo/scripts/backup/backup-full.ps1`
- `springboot-demo/scripts/backup/backup-incremental.ps1`
- `springboot-demo/scripts/backup/upload-cloud.ps1`
- `springboot-demo/scripts/backup/restore-from-backup.ps1`
- `springboot-demo/scripts/backup/cleanup-backups.ps1`
- `springboot-demo/scripts/backup/common.ps1`

### 5.2 `common.ps1`

职责：

- 提供公共函数
- 统一日志格式
- 统一时间戳格式
- 统一路径生成规则
- 统一 manifest 写入逻辑

建议函数：

- `Get-Timestamp`
- `Ensure-Directory`
- `Write-BackupLog`
- `Get-FileSha256`
- `Write-ManifestFile`
- `Read-BackupConfig`
- `Test-CommandExists`

### 5.3 `backup-full.ps1`

职责：

- 执行本地数据库全量导出

输入参数建议：

- `DbHost`
- `DbPort`
- `DbName`
- `DbUser`
- `DbPassword`
- `OutputRoot`
- `MySqlDumpPath`
- `Compress`
- `KeepLocalDays`

执行流程建议：

1. 加载公共配置
2. 检查 `mysqldump` 是否可用
3. 创建当日目录
4. 导出 SQL 文件
5. 计算哈希
6. 生成 manifest
7. 可选压缩
8. 写日志
9. 调用上传脚本

输出文件建议：

- `full_yyyyMMdd_HHmmss.sql`
- `full_yyyyMMdd_HHmmss.sql.zip`
- `full_yyyyMMdd_HHmmss.manifest.json`
- `logs/full_yyyyMMdd.log`

### 5.4 `backup-incremental.ps1`

职责：

- 归档增量日志

输入参数建议：

- `DbHost`
- `DbPort`
- `DbName`
- `DbUser`
- `DbPassword`
- `OutputRoot`
- `BinlogRoot`
- `Mode`

`Mode` 建议支持：

- `binlog`
- `snapshot`

执行流程建议：

1. 读取上次归档记录
2. 找到本次新增文件
3. 复制到归档目录
4. 计算哈希
5. 生成 manifest
6. 调用上传脚本
7. 写归档游标

### 5.5 `upload-cloud.ps1`

职责：

- 上传本地备份到云端

输入参数建议：

- `SourcePath`
- `CloudType`
- `CloudBucket`
- `CloudPath`
- `AccessKey`
- `SecretKey`
- `Region`

说明：

- `CloudType` 可以先做成抽象参数
- 第一版先预留接口，不强绑定具体云厂商
- 后续可按阿里云、腾讯云、华为云分别适配

执行流程建议：

1. 检查待上传文件是否存在
2. 检查云端配置是否完整
3. 执行上传
4. 记录远端路径
5. 返回上传结果

### 5.6 `restore-from-backup.ps1`

职责：

- 从指定备份执行恢复演练

输入参数建议：

- `BackupFile`
- `ManifestFile`
- `RestoreDbHost`
- `RestoreDbPort`
- `RestoreDbName`
- `RestoreDbUser`
- `RestoreDbPassword`
- `MySqlPath`

执行流程建议：

1. 校验备份文件存在
2. 校验 SHA256
3. 创建恢复数据库
4. 导入 SQL
5. 执行基础校验 SQL
6. 生成恢复报告

### 5.7 `cleanup-backups.ps1`

职责：

- 清理超期本地备份

输入参数建议：

- `OutputRoot`
- `KeepFullDays`
- `KeepIncrementalDays`
- `DryRun`

执行流程建议：

1. 扫描本地备份目录
2. 找出超期文件
3. 输出待清理清单
4. 非 `DryRun` 模式下执行删除
5. 写入清理日志

## 六、文件命名规范

建议统一命名：

- 全量备份：`full_yyyyMMdd_HHmmss.sql.zip`
- 增量备份：`inc_yyyyMMdd_HHmmss.sql.zip` 或 `inc_yyyyMMdd_HHmmss.zip`
- manifest：`full_yyyyMMdd_HHmmss.manifest.json`
- 恢复报告：`restore_yyyyMMdd_HHmmss.report.json`

manifest 建议字段：

- `backupType`
- `dbName`
- `generatedAt`
- `fileName`
- `fileSize`
- `sha256`
- `sourceHost`
- `appVersion`
- `mysqlVersion`
- `uploadStatus`
- `cloudPath`

## 七、定时任务建议

建议先采用操作系统定时任务：

- 每天 `02:00` 执行全量备份
- 每小时整点执行增量归档
- 每天 `03:00` 执行本地历史清理
- 每周执行一次恢复演练检查

如果后续部署到云主机或运维平台，再迁移到统一调度系统。

## 八、第一版使用示例

建议先复制配置模板，再按实际环境修改：

```powershell
Copy-Item `
  springboot-demo/scripts/backup/backup.config.example.json `
  springboot-demo/scripts/backup/backup.config.json
```

执行一次全量备份：

```powershell
cd springboot-demo
.\scripts\backup\backup-full.ps1 -ConfigPath "scripts/backup/backup.config.json"
```

执行一次增量备份：

```powershell
cd springboot-demo
.\scripts\backup\backup-incremental.ps1 -ConfigPath "scripts/backup/backup.config.json"
```

执行一次恢复演练：

```powershell
cd springboot-demo
.\scripts\backup\restore-from-backup.ps1 `
  -ConfigPath "scripts/backup/backup.config.json" `
  -BackupFile "target/backups/full/full_20260526_020000.sql.zip" `
  -DropIfExists
```

## 九、失败处理设计

任何脚本失败时，至少要做到：

1. 明确返回失败状态码
2. 把失败原因写入日志
3. 标记 manifest 为失败
4. 不覆盖已有成功备份
5. 触发告警

常见失败场景包括：

- `mysqldump` 不存在
- 数据库连接失败
- 本地磁盘空间不足
- 云端上传失败
- 校验值不一致
- 恢复导入失败

## 十、恢复验证清单

每次恢复演练至少校验：

- `product` 表记录数
- `customer` 表记录数
- `supplier` 表记录数
- `purchase_order` 表记录数
- `sales_order` 表记录数
- `inventory` 表记录数
- `inventory_log` 表记录数
- `operation_log` 表记录数

还要额外抽查：

- 随机一张采购单是否可查到
- 随机一张销售单是否可查到
- 库存总数是否可统计
- 用户是否能正常登录测试环境

## 十一、建议实施顺序

建议按以下顺序推进：

1. 先补本文档确认口径
2. 再创建脚本目录和公共配置
3. 先做全量备份脚本
4. 再做上传脚本
5. 再做恢复脚本
6. 最后补增量归档和清理脚本

原因很简单：

- 全量备份是最小可用能力
- 上传脚本决定云端是否真正落地
- 恢复脚本决定备份是否真正有效
- 增量归档是在“能备、能传、能恢复”之后再增强
