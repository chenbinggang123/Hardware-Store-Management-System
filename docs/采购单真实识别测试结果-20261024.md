# 三张采购单真实识别测试结果

测试日期：2026-10-24。使用原照片、项目配置的真实腾讯云OCR与对话模型。每张独立测试，无前一张单据上下文；测试仅开放百科查询、单据准备两个工具，调用真实草稿预览与规范化，不执行保存、不改商品、库存或账本。它验证图片到草稿内容链路，不等于完整微信交互、业务工具全集或多图连续对话验收。

结果：三张都完成OCR、主动查询百科并提交建单参数；前两张因整单备注超过200字而无法生成预览，第三张成功预览但仍有关键字段错误。整体尚未达到可放心使用的识别质量。

本次模型：deepseek-flash。耗时为本轮单次观测，不代表平均性能。

本轮没有做“关闭百科”的同条件对照，也没有经用户确认的完整标准答案，因此不计算识别准确率或百科提升百分比。成功生成预览仅代表程序接受了字段，不代表字段正确。

## 主要问题

1. 辉达单：数量格中的竖线/杂字符被识别为数字1，出现4→14、100→1100、80→180；单价4.5→45。小五保留部分验算疑点，但仍将错误数量写入参数。
2. 辉达单：第8行名称不清时，第9行错误回跳沿用第3行“镀钛钻头”，没有正确处理最近一组的未确定名称。
3. 前两张：小五将大量审核信息放入整单remark，超过200字，被校验拒绝。sourceNote虽有较长容量，仍未阻止此问题。
4. 林光0000855：把供应商地址填写为companyName（本应本店买方名称）；规格乘号被OCR漏掉，仅保留31-3、36-8。
5. 0000863：把票头客户“恒迪”当成供应商；OCR原文实际有2026、10、5，但模型只填年份，规范化后日期留空；气动管单价留空，多个规格仅存在rawSpecification，未进入可编辑规格栏。
6. 百科确实被调用，但无法恢复OCR丢失的笔画或小数点，也不能替代正确的表格行列解析。模型把部分直径候选直接填入规格，虽然备注待核对，仍未严格实现“候选待选”的呈现。

人眼对照只用于原图中较清楚的数量、单价和买卖方向；模糊品名、品牌、日期不视为已经确认的标准答案。下面保留所有实际输出，没有把人眼答案替换进测试结果。
