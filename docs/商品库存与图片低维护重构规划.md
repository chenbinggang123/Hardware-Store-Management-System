# 商品、库存与图片低维护重构规划

> 目标用户：没有专职库管、主要靠进货和销售维持数据的个体五金商户
> 产品原则：经营动作优先、异常才打扰、资料渐进补全、允许“不精确库存”
> 规划日期：2026-10-13

## 1. 现状判断

当前小程序把“商品”和“库存”分别放在底部导航中，但两个页面实际围绕同一对象：商品列表已经展示价格、库存和库位，库存列表又重复展示商品、数量和预警。用户需要在两个入口之间切换，才能完成一次商品查询或库存调整。

现有流程还默认商户会持续维护商品上架状态、多个价格、准确库存、预警线和库位。对多数个体商户而言，这些维护动作不会直接产生收入，很容易在忙碌时被放弃，最终形成“字段很多但数据不可信”的页面。

因此不应简单地把两个长列表拼接起来，而应同时调整导航、数据口径和日常工作流。

## 2. 产品决策

### 2.1 小五就是首页

取消独立首页和工作台。登录成功、重新进入小程序或点击第一个 Tab 时，直接进入小五。建议底部导航调整为：

| 入口 | 主要任务 | 说明 |
| --- | --- | --- |
| 小五 | 对话、拍照、处理文件、查询和执行 | 默认首页与产品核心，放在第一位 |
| 文件 | 查看、搜索和管理已处理文件 | 统一承载任务、原文件和生成结果 |
| 财务 | 查看客户/厂商往来账、已付和未付 | 独立一级入口，按对象和日期组织 |
| 商品 | 查商品、价格和库存，处理盘点与缺货 | 商品资料与库存合并为一个功能 |
| 我的 | 客户供应商、报表、设置和低频工具 | 收纳维护型功能 |

底部顺序固定为 `小五｜文件｜财务｜商品｜我的`。小五是连接文件、财务、商品和业务动作的核心；文件负责原件与处理过程，财务负责钱和往来余额，商品负责资料与库存，我的负责低频维护。

小五放在第一位，并作为登录后的落点。用户不需要先理解“上传文件”“记账”“导入商品”等模块，只需拍照、选择文件或说出需求，再由小五分流。不使用自定义凸起 Tab，保持小程序原生导航一致性。

### 2.2 商品与库存合并为“商品库”

合并后的商品库只在列表首屏展示决策所需信息：

- 商品图片或颜色占位图；
- 商品名称、规格和常用单位；
- 当前常用售价；
- 库存状态：`有货`、`不多`、`缺货`、`未记录`；
- 最近进货或销售时间；
- 快捷动作：`开单`、`调库存`、`更多`。

条码、批发价、老客户价、进价、换算关系、厂商、库位、上下架状态等放入详情页渐进展示，不再把列表做成缩小版数据库。

页面顶部只保留三个视图：

- `常用`：最近成交、最近进货或用户置顶的商品；
- `需处理`：缺货、库存冲突、未定价、待匹配商品；
- `全部`：搜索和完整商品库。

默认进入“常用”，不要求用户浏览全部商品。

### 2.3 库存改为“可信度 + 异常”，不强求实时精确

商品增加库存管理模式：

| 模式 | 适用情况 | 系统行为 |
| --- | --- | --- |
| 精确库存 | 高价值、易缺货、必须掌握数量 | 采购入库和销售出库自动增减，允许盘点 |
| 状态库存 | 大量低值散货 | 只记录有货/不多/缺货，不要求精确数量 |
| 不跟踪 | 按需采购或不值得维护 | 不显示库存预警，不阻止开单 |

默认新商品使用“状态库存”，而不是默认要求准确数量。只有用户明确盘点、扫码建档或业务需要时才切换为精确库存。

现有 `status=上架/下架` 从产品中移除：

- 所有未归档商品默认可用于查询和开单；
- 商品列表不显示上下架标签，不提供上下架筛选和操作；
- 需要清理历史资料时使用“归档”，归档不会删除订单、库存流水和价格记录；
- 开单时优先展示常用商品和有交易记录的商品；
- 数据迁移期间把现有商品统一转为可用，旧 `status` 字段暂时保留兼容，业务代码不再依赖它；稳定后再删除字段和相关接口。

### 2.4 系统自动维护，用户只处理例外

数据更新来源按优先级排列：

1. 销售单确认后自动记录最近售价、销量和最后销售时间；
2. 采购单或价格表确认后自动记录进价、供应商和库存变化；
3. 图片识别生成待确认商品或单据，不直接写正式数据；
4. 小五根据用户指令生成预览，确认后调整；
5. 手工编辑作为兜底，不作为主要入口。

系统只主动提醒：

- 精确库存商品低于阈值；
- 用户手动标记为“缺货”的常用商品；
- 销售时库存不足或长期未盘点；
- 新单据中出现未匹配商品；
- 同名、同条码或图片疑似重复商品。

不要展示“全部商品数”“已上架数”“库存总件数”等难以驱动行动的统计。

## 3. 图片保存功能

### 3.1 首期范围

首期支持每个商品一张主图，并在以下入口使用：

- 新增或编辑商品时拍照、从相册选择、删除或更换；
- 商品库缩略图；
- 商品详情大图预览；
- 开单选商品时作为辨认辅助；
- 小五搜索商品结果中展示缩略图（客户端根据商品 ID 补充显示）。

暂不首期实现多图图库、图片编辑器、公开分享链接和复杂图片分类。

### 3.2 存储设计

不再让用户手填“图片地址”。推荐复用小程序云存储上传能力：

```text
选择/拍摄图片
  → 客户端压缩与校验
  → wx.cloud.uploadFile
  → 得到稳定 cloudFileId
  → 调用商品图片接口保存 cloudFileId 和基础元数据
  → 商品页直接使用 cloudFileId 展示
```

建议增加 `product_image` 表，为将来多图和迁移 COS 留出空间：

| 字段 | 说明 |
| --- | --- |
| id | 图片记录 ID |
| product_id | 商品 ID，首期唯一 |
| cloud_file_id | CloudBase 文件 ID |
| object_key | 将来迁移 COS 时使用，可空 |
| original_name | 原文件名 |
| mime_type | 仅允许 JPEG、PNG、WebP |
| file_size | 压缩后大小 |
| width / height | 图片尺寸 |
| sha256 | 去重和完整性检查 |
| create_time / update_time | 时间 |

现有 `product.image_url` 在迁移期保留为兼容字段，接口优先返回新的图片视图；历史网络地址仍可显示，但不再允许表单直接输入。

客户端规则：

- 最多选择 1 张，上传前压缩，建议最长边 1600px；
- 压缩后不超过 3MB；
- 明确展示上传中、失败重试和删除状态；
- 更换成功后再删除旧云文件，避免保存失败导致图片丢失；
- 删除商品时由服务端返回需清理的文件 ID，客户端或云函数执行清理并记录失败重试。

后端接口建议：

```http
PUT    /api/products/{productId}/image/cloud
DELETE /api/products/{productId}/image
```

请求携带 `cloudFileId`、文件名、大小、MIME 和尺寸。服务端校验商品权限、类型、大小和文件 ID 格式，并写操作日志。不能信任客户端传来的网络 URL。

### 3.3 图片与识别的边界

“保存商品图片”和“识别价格表/单据图片”是两条流程：

- 商品图片用于辨认商品；
- 单据图片用于 OCR、核对和业务入账；
- OCR 附件不能自动成为商品主图；
- 可在复核页提供“设为商品图片”的明确操作，仍需用户确认目标商品。

## 4. 页面结构

### 4.1 小五：首页与统一入口

小五页面同时承担首页，但仍保持对话界面简洁。空会话状态只提供：

1. 输入框与拍照/选择文件按钮；
2. 三个高频建议：`处理一张单据`、`查往来账`、`查商品`；
3. 最多 3 条需要继续确认的任务；
4. `查看全部文件`和`查看财务`两个轻量入口。

建议结构：

```text
小五
有单据、价格表或经营问题，直接发给我

[＋ 拍照/文件]  [输入你想做什么……]

[处理一张单据] [查往来账] [查商品]

待继续
价格表.xlsx       等待核对       ›
送货单照片        识别失败 · 重试 ›

[全部文件 ›]              [财务 ›]
```

小五首页不展示经营仪表盘、销售统计、库存统计、工具宫格或已完成文件长列表。没有待办时保持留白，让输入框和附件按钮成为唯一视觉重点。

用户上传后由小五选择或建议用途：

- 识别并保存单据；
- 导入商品或价格；
- 生成 Excel；
- 只保存原文件；
- 交给小五阅读。

文件选择后直接作为当前小五会话的附件。小五先说明识别到的文件类型和建议动作，再由用户确认；只有流程明确且无需补充信息时，才进入专用复核页。用途不能确定时继续留在小五，而不是要求用户理解系统模块。

### 4.2 文件中心

文件中心是第二核心页面，统一原来的文件任务、生成文件和图片凭证：

- 顶部搜索文件名、供应商、单号和识别内容；
- 筛选仅保留 `待处理`、`已完成`、`失败`，文件类型放进次级筛选；
- 每条记录展示缩略图/类型、名称、处理目的、状态和更新时间；
- 点开后同时看到原文件、识别结果、生成文件和写入业务数据的记录；
- 支持继续处理、重新识别、下载/打开、重命名和删除；
- 默认按最近操作排序，不拆成多个互不相通的文件列表。

文件模型建议以一个统一的 `file_record` 或聚合视图为入口，关联现有 `excel_task`、`agent_attachment`、`excel_task_output` 和来源单据，避免首页分别请求和拼接多套文件数据。

#### 文件不是业务类型

图片、Excel、Word、PDF 只是文件格式，不能据此决定页面和流程。同一个格式可能对应完全不同的经营目的：

| 业务用途 | 常见内容 | 处理结果 |
| --- | --- | --- |
| 供应商价格表 | 商品、规格、单位、进价 | 待核对价格清单，可匹配商品并更新价格 |
| 商品资料表 | 商品名称、条码、图片、售价 | 待新增或补全的商品资料 |
| 采购/进货单据 | 供应商、商品、数量、金额 | 采购凭证、库存变化或工厂账本记录 |
| 客户单据 | 客户、商品、金额、欠款 | 客户往来凭证，可关联客户和销售记录 |
| 销售/收款单据 | 销售明细、实收、未收 | 销售记录、收款记录或待确认草稿 |
| 商品照片 | 外观、包装、型号 | 商品主图、识别候选或单纯留档 |
| 普通资料 | 合同、说明、聊天截图等 | 仅保存、阅读问答或生成新文件 |
| 暂未识别 | 内容不足或类型不确定 | 留在收件箱，等待用户选择或补充说明 |

文件中心不按“图片/Excel/PDF”建立一级文件夹，也不要求上传前先选择业务类型。首层只按状态组织：

- `待处理`：尚未确认用途、等待核对、需要补充信息或处理失败；
- `已整理`：已完成识别和整理，但不一定写入业务数据；
- `已关联`：已经关联商品、供应商、客户、采购、销售或账本；
- `全部`：搜索和追溯。

业务用途使用可多选标签和关联关系表达。例如一份供应商价格表可以同时关联“供应商”“商品价格”和“生成的 Excel”，而不需要复制成三份文件。

#### 小五负责判断和分流

上传后小五先给出可修改的判断，而不是直接写入：

```text
看起来是“锐恒五金”的商品价格表，共识别 36 行。

你想怎么处理？
[核对并更新商品价格]
[只整理成 Excel]
[保存到供应商资料]
[不是这个类型]
```

判断需要包含：

- 建议业务用途与置信度；
- 识别出的供应商或客户候选；
- 识别出的商品行数和未匹配数量；
- 可能产生的数据变化；
- “只保存、不写业务数据”的安全选项；
- 更正分类和补充说明入口。

小五的分类只是建议。商品、价格、库存、欠款或订单发生变化前，仍必须进入对应确认流程。

#### 单据的核心是往来账

客户单据和厂商单据不应只被当作销售单或采购单归档。它们首先是往来账凭证，用来回答：

- 对方是谁；
- 单据发生日期；
- 这张单据应收或应付多少；
- 已经支付多少；
- 还剩多少；
- 后续每次付款发生在什么日期；
- 原始凭证和付款凭证在哪里。

必须显式记录资金方向，不能仅根据“客户”或“厂商”推断：

- `RECEIVABLE`：对方欠我们；
- `PAYABLE`：我们欠对方。

当前业务可默认把客户或厂商单据建议为“对方欠我们”，但确认卡必须显示方向并允许修改，避免厂商采购账被误记成应收。

单据确认卡建议直接展示：

```text
往来对象：宏达模具厂（厂商）
单据日期：2026-10-12
账款方向：对方欠我们
单据金额：¥8,600.00
已付金额：¥3,000.00
剩余金额：¥5,600.00

[确认记入往来账] [修改金额或方向] [只保存文件]
```

“已付金额”不能只作为单据上的一个可覆盖字段。系统应保存独立付款流水；余额由单据金额减去关联付款累计计算。后续新增付款时追加流水，保留日期、金额、支付方式、备注和凭证文件，不直接改写历史付款。

#### 往来账查看方式

单据最终主要按“往来对象”和“日期”查看，而不是按文件格式查看：

```text
往来账
[客户] [厂商] [全部]

宏达模具厂
对方欠我们 ¥5,600
最近单据 10月12日 · 最近付款 10月15日

老王五金店
对方欠我们 ¥1,280
最近单据 10月10日 · 尚未付款
```

进入对象详情后：

- 顶部展示累计应收/应付、累计已付和当前余额；
- 按月份分组，月份内按日期倒序；
- 同一天的单据和付款按时间线排列；
- 每笔账可打开原始单据图片、识别结果和付款凭证；
- 支持记录付款、修正关联对象、作废错误记录和导出对账单；
- 客户与厂商仅是对象类型，列表和计算逻辑共用一套往来账模型。

#### 一个文件，一条完整时间线

文件详情以时间线呈现，不把过程拆散到多个模块：

```text
原始文件已保存
  ↓
小五识别为供应商价格表
  ↓
用户确认供应商“锐恒五金”
  ↓
匹配 32 个商品，4 个待处理
  ↓
已生成核对版 Excel
  ↓
用户确认更新 28 个商品价格
```

每一步都能看到操作者、时间、结果和关联对象；删除原文件前提示哪些识别结果或业务记录仍会保留。

### 4.3 财务

财务作为独立一级页面，只回答钱和往来关系，不混入文件处理进度或商品维护：

```text
财务
应收 ¥28,600    已收 ¥16,300    待收 ¥12,300

[客户] [厂商] [全部]

宏达模具厂       待收 ¥5,600   ›
老王五金店       待收 ¥1,280   ›
新建五金         已结清         ›
```

财务首页提供：

- 应收、已收、待收汇总；若启用应付，则分开显示，禁止净额抵消；
- 客户、厂商和全部筛选；
- 按名称搜索；
- 按最近发生、欠款最高或日期排序；
- “记录付款”和“生成对账单”高频动作；
- 对象未匹配、金额冲突、疑似重复和超额付款等异常提示。

进入客户或厂商后按月份和日期查看单据与付款流水，并能打开原始凭证。文件中心回答“这份文件处理到哪一步”，财务回答“这个对象目前欠多少、付了多少”；两者通过关联互相跳转，但不混成同一个列表。

### 4.4 商品库

```text
商品库
[搜索名称 / 条码 / 厂商] [扫码]
[常用] [需处理] [全部]

图片  冲击钻 680W
      ¥268 · 有货
      最近售出：昨天
      [开单] [调库存] [更多]
```

列表采用紧凑行而不是大卡片；缩略图固定尺寸，文字最多两行。缺少图片时显示由商品名称生成的稳定色块，不用空白占位图。

商品与库存的职责在同一页面内明确分层：

- 商品资料回答“这是什么、怎么卖、从哪里进”；
- 库存状态回答“现在有没有、放在哪里、上次何时核对”；
- 列表只显示两类信息的摘要；
- 点“调库存”直接进入盘点，不再先进入另一套库存列表；
- 点商品进入统一详情，在同一详情内查看库存流水，不再维护独立库存详情入口的重复商品信息。

### 4.5 商品详情

首屏仅展示图片、名称、规格、售价和库存状态；下面按需展开：

- 最近交易；
- 价格与客户价；
- 库存和盘点记录；
- 供应商与进货记录；
- 条码、单位换算、库位等资料。

主要操作固定为“开单”和“调整”，编辑资料进入更多菜单。

### 4.6 库存处理

删除独立库存首页，但保留库存详情、盘点和日志能力。入口来自：

- 商品库“需处理”；
- 商品详情；
- 商品“需处理”视图或小五提醒；
- 小五确认卡；
- 定期盘点任务。

## 5. 数据和接口调整

建议在 `product` 增加：

- `inventory_mode`: `EXACT`、`STATUS`、`NONE`；
- `stock_state`: `IN_STOCK`、`LOW`、`OUT_OF_STOCK`、`UNKNOWN`；
- `last_sold_at`、`last_purchased_at`；
- `archived_at`；
- 可选 `pinned` 或独立用户偏好表。

保留 `inventory.quantity` 和流水表，供精确库存商品使用。短期继续同步 `product.stock`，中期应明确 `inventory.quantity` 为唯一数量来源，避免两个字段漂移。

新增聚合查询，避免客户端同时请求商品和库存再自行拼接：

```http
GET /api/catalog?view=frequent|attention|all&keyword=&page=&size=
```

返回列表直接需要的商品、图片、价格、库存状态、最近交易时间和异常原因。列表必须分页，不能一次加载所有商品。

统一文件入口建议增加以下概念：

- `file_record`：一份原始文件的稳定身份、存储位置、哈希、所有者和状态；
- `file_classification`：小五建议的业务用途、置信度、用户最终选择和说明；
- `file_relation`：文件与商品、供应商、客户、采购单、销售单、账本和生成文件的多对多关联；
- `file_activity`：上传、识别、分类、核对、生成、写入和失败重试的时间线。

往来账建议使用统一模型，而不是分别在客户和厂商表保存一个可直接编辑的欠款总数：

- `counterparty` 或兼容关联：对象类型 `CUSTOMER` / `SUPPLIER` 与对象 ID；
- `account_document`：单据日期、方向、原始金额、币种、状态和来源文件；
- `account_payment`：付款日期、金额、方式、备注和付款凭证；
- `account_allocation`：一笔付款分配到一张或多张单据的金额；
- 当前余额通过有效单据与付款分配汇总得到，可建立只读汇总表或缓存字段提升查询性能。

关键约束：

- 金额统一使用 `BigDecimal`，禁止浮点计算；
- 剩余金额不得小于零，超额付款必须明确作为预收/预付或等待分配；
- 同一文件哈希、对象、日期、单号和金额高度相似时提示疑似重复；
- 修改已确认账款采用冲正或版本记录，不静默覆盖原值；
- 对象不确定时先进入待确认，不能自动新建客户或厂商；
- 所有汇总数字都能追溯到单据和付款流水。

不要立刻删除现有 `excel_task`、`agent_attachment` 和 `excel_task_output`。首期建立聚合层和关联表，让旧流程继续工作；确认统一模型稳定后，再逐步迁移。

## 7. 验收指标

- 底部导航不再同时出现商品和库存；
- 商品资料、库存数量/状态、库位、盘点和库存流水均完整保留；
- 用户无需维护上下架，未归档商品默认可用；
- 用户登录后直接看到小五输入框和拍照/文件按钮；
- 用户上传文件后无需先选择专业模块，可直接与小五继续交互；
- 小五在底部导航第一位并作为默认落点；
- 小五空会话页除待继续任务外不展示经营统计、工具宫格或已完成文件长列表；
- 财务拥有独立一级入口，可按客户/厂商和日期查看应收、已收与待收；
- 同一个文件的原件、识别结果、生成文件和业务写入记录能在一个详情中追溯；
- 一份文件可同时关联客户/供应商、商品、单据和生成结果，无需复制文件；
- 小五判断错误时用户可以更正用途，且更正前不会修改正式业务数据；
- 客户和厂商往来账均可按对象、月份和日期追溯；
- 任一余额都能展开到原始单据与付款流水；
- 新增付款不会覆盖历史已付金额，超额付款有明确去向；
- 查找常用商品无需浏览完整列表；
- 状态库存和不跟踪库存不会触发错误的数量预警；
- 上传图片失败不会覆盖已有图片，也不会留下不可见的商品状态；
- 商品库首屏接口分页返回，不依赖客户端二次拉取全量库存；
- 用户一周不手工维护商品资料，销售和采购流程仍能自动更新常用商品、价格和库存状态；
- 旧库存详情、盘点和日志数据完整保留。

## 8. 本轮不做

- 不把系统改造成面向连锁零售的 SKU/POS/仓库管理平台；
- 不要求所有商品都有图片、条码、精确库存和完整价格；
- 不自动根据 OCR 结果覆盖商品主图或正式库存；
- 不一次删除旧接口和旧页面，先完成兼容迁移并观察使用情况。
