# 五金店管理系统数据安全规划设计

## 一、文档定位

本文档基于当前仓库的实际实现，对五金店管理系统的数据安全建设进行规划设计。

本次设计不只讨论原则，还要回答三个问题：

- 当前代码已经做到什么程度
- 当前最容易出问题的地方在哪里
- 应该按什么顺序落地，才能在现阶段成本可控的前提下，把数据可靠性真正做起来

本文档面向以下对象：

- 后端开发
- 数据库设计与维护人员
- 项目负责人
- 后续验收与运维人员

如果需要进一步执行云端灾备落地，请配合阅读：

- `docs/云数据库备份实施方案.md`

## 二、设计依据与审计范围

本次规划已结合以下实际文件进行审计：

- 后端配置：`springboot-demo/src/main/resources/application.properties`
- MySQL 配置：`springboot-demo/src/main/resources/application-mysql.properties`
- 建表脚本：`springboot-demo/src/main/resources/schema.sql`
- 初始化数据：`springboot-demo/src/main/resources/data.sql`
- 采购事务实现：`springboot-demo/src/main/java/com/example/demo/service/impl/PurchaseOrderServiceImpl.java`
- 销售事务实现：`springboot-demo/src/main/java/com/example/demo/service/impl/SalesOrderServiceImpl.java`
- 登录实现：`springboot-demo/src/main/java/com/example/demo/service/impl/AuthServiceImpl.java`
- 内存存储实现：`springboot-demo/src/main/java/com/example/demo/service/impl/support/ApplicationMemoryStore.java`

本轮重点覆盖：

- 用户
- 商品
- 客户
- 供应商
- 采购单
- 销售单
- 库存
- 库存流水
- 操作日志
- 报表导出

本轮不处理：

- 小程序视觉层安全设计
- 多机房或分布式容灾
- 复杂消息中间件架构升级
- 超出当前项目体量的高成本合规体系

## 三、当前现状审计结论

### 3.1 已有基础能力

当前项目已经具备一部分可继续沿用的数据安全基础：

- 后端已切换到 Spring Boot + JPA + MySQL 模式
- 采购和销售服务已经使用 `@Transactional`
- 商品、订单、库存、日志等核心表已经有基础表结构
- 采购入库、销售出库、收款登记已经具备初步业务联动逻辑
- 已存在 `inventory_log` 和 `operation_log` 两类日志表
- 报表接口已经有统一后端出口，便于后续扩展导出能力

这意味着系统不是从零开始，后续应以“补强和收敛”为主，而不是完全推倒重来。

### 3.2 当前高风险问题

结合现有代码与 SQL，当前最需要优先处理的问题如下。

#### 3.2.1 数据初始化策略存在覆盖风险

当前 `application-mysql.properties` 中配置了：

- `spring.sql.init.mode=always`

这意味着应用启动时会重复执行 `schema.sql` 和 `data.sql`。

配合当前 `data.sql` 中大量 `ON DUPLICATE KEY UPDATE` 语句，存在以下风险：

- 生产或测试环境启动时重复覆盖演示数据
- 初始化账号、商品、订单被反复写回
- 真实业务数据与演示数据混杂
- 环境切换时无法明确“哪些是业务数据，哪些是种子数据”

这属于当前最直接的数据安全风险之一。

#### 3.2.2 用户密码仍为明文存储和明文比对

当前 `app_user` 表中的密码来自 `data.sql` 明文初始化，`AuthServiceImpl` 中也直接使用明文比较。

主要风险：

- 数据库泄漏时用户密码直接暴露
- 无法满足最基本的账号安全要求
- 后续若引入更多角色账号，风险会被放大

#### 3.2.3 库存存在双写源，不利于一致性

当前库存相关数据同时存在于：

- `product.stock`
- `inventory.quantity`

采购入库和销售出库时，两张表会一起更新。这样虽然短期方便，但会带来两个问题：

- 一旦某次变更只改了一张表，就会出现账实不一致
- 后续做盘点、报表、预警时，很难明确哪个字段才是最终口径

因此必须明确唯一库存真源。

#### 3.2.4 订单明细存放在 JSON 字段，约束能力不足

当前采购单和销售单明细保存在：

- `purchase_order.items_json`
- `sales_order.items_json`

这种设计适合早期快速开发，但存在明显限制：

- 无法通过数据库约束保证每条明细完整
- 无法直接建立明细级索引
- 不利于按商品、时间、订单维度做精确统计
- 不利于审计和问题回查

#### 3.2.5 关键表缺少更新字段、逻辑删除字段和版本控制字段

当前多数核心表只有 `create_time`，缺少：

- `update_time`
- `delete_time`
- `deleted`
- `version`

由此带来的问题包括：

- 无法准确判断最后修改时间
- 无法优雅支持逻辑删除
- 并发更新时缺少版本保护
- 审计成本高

#### 3.2.6 外键与索引约束偏弱

当前建表脚本主要依赖主键与少量唯一键，尚未系统补齐：

- 外键约束
- 常用筛选索引
- 状态字段索引
- 时间范围索引

这会导致：

- 脏数据更容易进入数据库
- 查询性能和导出性能不稳定
- 数据关系只能依赖代码约束，数据库本身防护不足

#### 3.2.7 审计日志信息粒度不够

当前 `operation_log` 只有：

- 操作人
- 模块
- 动作
- 简要描述
- 时间

这对“知道发生过什么”是够的，但对“查清到底改了什么”还不够。

缺失内容主要包括：

- 目标对象类型
- 目标对象 ID
- 请求来源
- 操作前后关键摘要
- 失败操作记录

#### 3.2.8 备份与恢复还停留在人工初始化阶段

当前仓库提供的是数据库初始化脚本，不是正式备份方案。

缺失内容包括：

- 全量备份脚本
- 恢复脚本
- 备份保留策略
- 备份结果登记
- 恢复演练标准流程

#### 3.2.9 导出能力仍偏“报表返回”，不是真正的数据导出方案

当前 `ReportServiceImpl#exportReport` 仍返回说明性结构，没有形成标准化导出能力。

当前不足主要体现在：

- 没有固定字段清单
- 没有统一文件格式
- 没有导出权限控制
- 没有导出操作审计

#### 3.2.10 仓库中仍保留内存存储实现，易造成认知分裂

当前代码里仍存在 `ApplicationMemoryStore` 等内存存储类。

虽然主业务已走 JPA，但这些代码会带来两个隐患：

- 新开发者可能误以为系统仍允许以内存为主
- 后续维护时容易出现新旧实现混用

因此应在方案中明确其定位：废弃、隔离或移除。

## 四、数据安全建设目标

本系统数据安全建设目标定义如下：

### 4.1 总体目标

建立一套适合当前项目阶段、可在单体 Spring Boot + MySQL 架构下落地的数据安全体系，确保核心经营数据：

- 可稳定保存
- 可一致写入
- 可审计追溯
- 可备份恢复
- 可标准导出

### 4.2 具体目标

1. 以后端数据库作为唯一可信数据源
2. 关键业务写入全程事务化
3. 核心主数据默认不做物理删除
4. 关键变更可按人、按时间、按对象追溯
5. 发生误删、误改、部署异常后可恢复
6. 经营数据可由后端统一稳定导出
7. 账号和敏感配置满足基础安全要求

## 五、总体设计原则

### 5.1 先收口，再增强

优先统一数据真源、统一写入口、统一导出口，再做更细的优化。

### 5.2 以数据库约束兜底，以服务事务保证联动

数据库负责兜底防脏数据，服务层负责保证跨表一致性。

### 5.3 可恢复优先于可炫技

对于当前项目阶段，最重要的是数据出问题后能恢复，而不是过早引入复杂基础设施。

### 5.4 关键对象默认留痕

对商品、客户、供应商、订单、库存、用户的关键操作，默认要求可追踪。

### 5.5 开发环境和正式环境必须分策略

演示初始化、调试便利、种子数据，只允许留在开发环境，不得直接沿用到生产方案。

## 六、目标架构设计

### 6.1 数据源架构

目标口径如下：

- MySQL 为唯一核心数据源
- 前端缓存仅做展示缓存，不做最终写入依据
- 报表、导出、库存预警均从数据库读取
- 内存存储类不再承载正式业务数据

### 6.2 核心数据分层

建议将数据划分为四类：

1. 主数据
   商品、客户、供应商、用户
2. 交易数据
   采购单、销售单、收款记录、库存流水
3. 控制数据
   状态字段、版本字段、逻辑删除字段、审计字段
4. 运维数据
   操作日志、备份记录、导出记录

### 6.3 数据真源定义

建议明确以下真源规则：

- 商品基础信息以 `product` 为准
- 库存数量以 `inventory` 为准
- 库存变更历史以 `inventory_log` 为准
- 采购单主信息以 `purchase_order` 为准
- 销售单主信息以 `sales_order` 为准
- 客户欠款以销售单欠款汇总结果为准
- 操作追踪以 `operation_log` 和扩展审计日志为准

其中：

- `product.stock` 在下一阶段应改为冗余展示字段，或逐步移除
- 不能再把 `product.stock` 和 `inventory.quantity` 同时视作独立真源

## 七、详细设计方案

### 7.1 配置与环境安全设计

#### 7.1.1 环境分层

建议将环境拆分为：

- 开发环境
- 测试环境
- 生产环境

要求如下：

- 开发环境可保留种子数据初始化
- 测试环境只允许一次性初始化，不允许每次启动覆盖
- 生产环境禁止 `spring.sql.init.mode=always`

建议配置策略：

- `dev`：允许 `always` 或 `embedded`
- `test`：改为 `never`，初始化由脚本显式执行
- `prod`：必须 `never`

#### 7.1.2 配置外置化

以下信息不得再长期硬编码在默认配置中：

- 数据库密码
- root 账号口令
- 默认业务账号口令

建议改为：

- 环境变量
- 独立配置文件
- 部署平台密钥管理

### 7.2 账号与认证安全设计

#### 7.2.1 密码存储

建议将 `app_user.password` 改造为密码哈希字段，例如：

- `password_hash`

实现要求：

- 使用 BCrypt
- 登录时使用哈希校验
- 不再保存明文密码
- 初始化脚本中的演示账号也必须写入哈希值

#### 7.2.2 用户状态管理

建议补充以下字段：

- `update_time`
- `last_login_time`
- `last_password_change_time`

后续可扩展：

- `login_fail_count`
- `lock_until`

#### 7.2.3 权限最小化

至少区分：

- 管理员
- 店员

建议约束：

- 删除、恢复、导出、手工库存调整仅管理员可执行
- 普通店员可新增业务单据，但高风险动作需要限制

### 7.3 表结构与字段规范设计

#### 7.3.1 通用字段规范

建议核心表统一补齐：

- `create_time`
- `update_time`
- `deleted`
- `delete_time`
- `version`

适用表包括：

- `product`
- `supplier`
- `customer`
- `inventory`
- `purchase_order`
- `sales_order`
- `app_user`

说明：

- `deleted` 用于逻辑删除
- `version` 用于乐观锁控制

#### 7.3.2 主键与业务编号规范

保留双标识体系：

- `id` 作为内部主键
- `order_number` 作为外部展示编号

要求：

- 编号全局唯一
- 编号生成逻辑稳定
- 避免仅用秒级时间戳生成，防止高并发碰撞

建议：

- 增加日期前缀 + 序列号
- 或由独立号段服务在单体内实现

#### 7.3.3 金额与数量字段规范

要求：

- 金额统一使用 `DECIMAL(12,2)` 或更高精度
- 数量统一使用 `INT` 或 `DECIMAL`，按业务含义固定
- 禁止金额使用浮点类型

建议优先调整：

- `product` 价格类字段
- `purchase_order.total_amount`
- `sales_order.total_amount`
- `received_amount`
- `debt_amount`

#### 7.3.4 状态字段规范

状态字段必须收敛，避免自由文本失控。

建议统一枚举范围：

- 采购单状态：`DRAFT`、`PENDING_STOCK_IN`、`STOCKED_IN`、`CANCELLED`
- 销售单状态：`DRAFT`、`PENDING_STOCK_OUT`、`STOCKED_OUT`、`CANCELLED`
- 支付状态：`UNPAID`、`PARTIAL`、`PAID`
- 用户状态：`ENABLED`、`DISABLED`

前端展示可转中文，数据库内部建议逐步收敛为稳定码值。

### 7.4 核心数据模型设计

#### 7.4.1 商品与库存模型

建议原则：

- `product` 管主数据
- `inventory` 管库存真值

下一阶段处理策略：

1. 短期保留 `product.stock`，但仅作为同步冗余字段
2. 所有库存变更只允许通过库存服务统一执行
3. 中期将查询口径迁移为 `inventory.quantity`
4. 条件成熟后移除 `product.stock` 或明确标注为缓存字段

#### 7.4.2 订单主表与明细表

建议将订单明细从 JSON 迁移为结构化子表：

- `purchase_order_item`
- `sales_order_item`

建议字段至少包括：

- `id`
- `order_id`
- `product_id`
- `product_name_snapshot`
- `price`
- `quantity`
- `amount`
- `location_id`
- `create_time`

迁移收益：

- 可加外键和索引
- 可做明细级审计
- 可支持精确导出
- 可支持商品维度统计

短期过渡方案：

- 保留 `items_json` 兼容读取
- 新数据优先写结构化明细
- 完成迁移后再移除 JSON 字段

#### 7.4.3 收款记录模型

当前 `registerPayment` 只更新销售单金额汇总，缺少独立收款流水。

建议新增收款记录表，例如：

- `account_record`

建议字段：

- `id`
- `sales_order_id`
- `customer_id`
- `payment_method`
- `received_amount`
- `operator_id`
- `remark`
- `create_time`

这样可以解决：

- 收款历史无法逐笔追踪
- 无法回看每次收款方式和时间
- 无法做准确对账

### 7.5 事务一致性设计

#### 7.5.1 采购入库事务

当前采购服务已具备事务基础，后续应明确事务边界包含：

- 校验采购单状态
- 校验商品有效性
- 写采购主表
- 写采购明细表
- 更新库存
- 写库存流水
- 写操作日志

要求：

- 任一步失败整体回滚
- 已入库采购单禁止重复入库
- 重复请求需具备幂等保护

#### 7.5.2 销售出库事务

当前销售服务已具备事务基础，后续应增强：

- 出库前库存校验
- 并发扣减保护
- 销售主表与明细表统一提交
- 库存流水与操作日志统一提交

建议增加以下保护机制之一：

- 基于 `version` 的乐观锁
- 基于数据库行锁的悲观锁

目标是避免并发下超卖。

#### 7.5.3 收款登记事务

收款登记应纳入统一事务，边界应覆盖：

- 写收款记录
- 更新销售单已收金额
- 更新欠款金额
- 更新支付状态
- 汇总更新客户欠款
- 写操作日志

#### 7.5.4 删除与作废事务

关键业务对象默认不做直接物理删除。

建议策略：

- 商品、客户、供应商、用户使用逻辑删除或停用
- 已入库采购单、已出库销售单只允许作废标记，不允许硬删除
- 只有无业务关联测试数据才允许物理删除

### 7.6 审计与日志设计

#### 7.6.1 操作日志增强

建议扩展 `operation_log` 字段：

- `target_type`
- `target_id`
- `target_code`
- `result`
- `request_id`
- `ip`
- `before_snapshot`
- `after_snapshot`

本轮可先实现轻量版：

- `target_type`
- `target_id`
- `result`

#### 7.6.2 必须留痕的动作

以下动作建议强制写日志：

- 登录
- 登出
- 商品新增
- 商品修改
- 商品停用
- 客户修改
- 供应商修改
- 采购单创建、修改、入库、作废
- 销售单创建、修改、出库、作废
- 收款登记
- 库存手工调整
- 导出操作
- 备份与恢复操作

#### 7.6.3 审计日志与业务日志分层

建议区分两类日志：

- 业务操作日志
  记录谁做了什么
- 数据审计日志
  记录关键字段前后变化

本轮先完成业务操作日志增强，下轮再扩展字段级审计。

### 7.7 备份与恢复设计

#### 7.7.1 备份目标

目标是满足以下场景恢复：

- 误删
- 误改
- 应用升级异常
- 数据库实例损坏
- 迁移失败

#### 7.7.2 备份策略

建议分阶段实施。

第一阶段：

- 每日全量备份
- 保留最近 7 天
- 备份文件带时间戳
- 备份目录与应用目录分离

第二阶段：

- 每周归档备份
- 保留最近 4 周
- 重要环境增加异机备份

建议备份内容：

- 数据库全量 SQL dump
- 必要配置文件
- 备份执行日志

在引入云数据库后，备份策略建议升级为“双副本”：

- 本地数据库保留日常运行主副本
- 云数据库承担异地灾备副本或恢复目标
- 本地备份文件用于快速回滚
- 云端备份用于机器损坏、磁盘损坏、机房故障后的恢复

不建议把“云数据库中再建一套表并手工导入”当作唯一备份方式，更建议采用：

- 本地主库 + 云端定时全量备份
- 本地主库 + 云端增量日志备份
- 本地主库 + 云端热备实例

当前项目阶段，最适合先落地的是：

- 本地主库 + 云端每日全量备份
- 重要时段增加云端每小时增量备份

#### 7.7.3 恢复流程

恢复流程建议标准化为：

1. 暂停系统写入
2. 记录当前故障时间和影响范围
3. 选择备份版本
4. 在隔离环境先试恢复
5. 校验核心表数量和关键订单
6. 正式恢复
7. 验证采购、销售、库存、登录链路
8. 记录恢复结论

#### 7.7.4 备份台账

建议新增备份记录表或文件台账，至少记录：

- 备份批次号
- 环境
- 开始时间
- 结束时间
- 文件路径
- 文件大小
- 执行结果
- 执行人

#### 7.7.5 云数据库备份架构

如果明确希望将数据备份到云数据库，建议采用以下架构：

1. 门店或本地服务器中的 MySQL 作为主业务库
2. 云数据库作为异地灾备库
3. 通过定时任务将全量备份文件上传云端
4. 通过 binlog 或增量同步机制减少恢复点丢失
5. 恢复时优先从最近全量备份 + 最近增量日志还原

建议分三种实现级别：

第一种：低成本方案

- 每日把 SQL 备份文件上传到云服务器或对象存储
- 云端不保持实时可查询数据库
- 优点是成本低、实现简单
- 缺点是恢复时间较长

第二种：标准方案

- 每日全量备份到云端
- 每小时或每 15 分钟同步增量日志
- 云上保留可恢复的 MySQL 实例
- 优点是恢复点更近，适合正式经营环境

第三种：增强方案

- 本地主库持续向云数据库同步
- 云端保持热备实例
- 故障时切换到云库继续服务
- 优点是恢复速度快
- 缺点是实施和运维成本更高

对于当前项目体量，建议优先采用第二种标准方案。

#### 7.7.6 云端备份内容要求

云端备份不应只保存业务表，还应一并覆盖以下内容：

- `product`
- `supplier`
- `customer`
- `purchase_order`
- `sales_order`
- `inventory`
- `inventory_log`
- `operation_log`
- 后续新增的 `purchase_order_item`
- 后续新增的 `sales_order_item`
- 后续新增的 `account_record`

同时建议保存：

- 当前应用版本号
- 备份时使用的数据库版本
- 核心配置快照
- 备份校验结果

#### 7.7.7 云端备份安全要求

数据放到云数据库后，必须补充以下安全控制：

- 云数据库实例禁止公网裸开放
- 仅允许白名单 IP 或专线访问
- 备份传输过程使用加密连接
- 云端备份账号与业务读写账号分离
- 备份账号仅授予最小权限
- 关键备份文件建议再次加密
- 备份和恢复操作必须写入审计日志

如果未来云端保存客户手机号、地址、账款等敏感信息，建议进一步增加：

- 备份文件加密密钥轮换
- 云端访问审计
- 管理员双人确认恢复机制

#### 7.7.8 云数据库恢复目标

采用云数据库备份后，建议明确两个恢复指标：

- RPO：可接受的数据丢失时间
- RTO：可接受的恢复时长

结合当前业务，建议初始目标如下：

- RPO 不超过 1 小时
- RTO 不超过 4 小时

如果后续门店业务量上升，再进一步收紧为：

- RPO 不超过 15 分钟
- RTO 不超过 1 小时

#### 7.7.9 云数据库落地步骤

建议按以下顺序实施：

1. 保持本地 MySQL 作为当前主库不变
2. 在云端准备独立 MySQL 实例作为灾备库
3. 编写全量备份脚本并验证可恢复
4. 编写增量同步或 binlog 归档脚本
5. 增加备份结果记录与失败告警
6. 做一次完整恢复演练
7. 再决定是否升级为云端热备

### 7.8 导出能力设计

#### 7.8.1 导出范围

本轮建议优先支持：

- 商品导出
- 客户导出
- 供应商导出
- 采购单导出
- 销售单导出
- 库存导出
- 操作日志导出

#### 7.8.2 导出规则

统一要求：

- 字段顺序固定
- 字段名稳定
- 支持时间范围筛选
- 支持状态筛选
- 支持关键字筛选
- 空值处理一致
- 导出动作写审计日志

#### 7.8.3 导出格式

分两步推进：

第一步：

- JSON 导出
- CSV 导出

第二步：

- Excel 导出

不建议继续只返回“导出说明文本”，应返回真实可消费的数据文件或标准数据流。

## 十、验收标准

本轮数据安全建设完成后，应至少满足以下标准：

1. 正式环境启动不会自动覆盖业务数据
2. 用户密码不再以明文存储
3. 库存真源唯一且口径明确
4. 采购、销售、收款具备稳定事务保护
5. 主数据默认逻辑删除或停用
6. 关键业务操作可按人、按时间、按对象追踪
7. 具备至少一套可执行的备份与恢复流程
8. 商品、客户、订单、库存支持统一后端导出
9. 云端至少保留一份可恢复的异地备份
10. 已完成一次从云端备份恢复的演练验证

## 十一、最终结论

当前项目最务实的数据安全路径，不是引入复杂架构，而是优先把以下六件事做扎实：

- 关闭危险的自动初始化覆盖
- 改造明文密码
- 统一库存真源
- 结构化订单明细
- 补齐审计与备份恢复
- 建立统一导出能力

如果你决定把备份放到云数据库，建议采用“本地主库 + 云端灾备库”的方式推进，而不是直接把云库当作一个普通导出目标。这样后续无论是误删恢复、服务器损坏还是迁移上线，都会更稳。

如果这六件事按阶段落地，当前系统的数据可靠性、可恢复性和可维护性都会明显提升，也能为后续正式部署和业务扩展打下更稳的基础。
