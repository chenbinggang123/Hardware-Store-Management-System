# 五金店管理系统数据安全设计

## 一、文档目标

本文档用于定义五金店管理系统在数据库层面的数据安全建设方案，重点解决以下问题：

- 核心业务数据如何稳定保存，避免丢失
- 数据误删、误改后如何追溯和恢复
- 关键业务写入如何保证一致性
- 数据如何安全备份与恢复
- 数据如何稳定导出，支持经营分析与归档

本文档既是数据库工作区的设计依据，也是后续开发、验收和运维的参考标准。

## 二、适用范围

本设计适用于当前仓库中的后端与数据层，重点覆盖：

- 后端目录：`springboot-demo`
- SQL 初始化脚本：`springboot-demo/src/main/resources/schema.sql`
- 初始化数据脚本：`springboot-demo/src/main/resources/data.sql`
- 实体、仓库、服务、控制器中的数据写入逻辑

本轮不处理以下事项：

- 小程序页面视觉设计
- 无边界分布式架构升级
- 非数据库方向的前端重构
- 与当前业务体量不匹配的高复杂度中间件改造

## 三、当前业务数据范围

当前系统的核心业务数据主要包括：

- 用户数据
- 商品数据
- 供应商数据
- 客户数据
- 采购单与采购明细
- 销售单与销售明细
- 库存与库存流水
- 操作日志
- 报表导出相关数据

这些数据中，采购、销售、库存、商品、客户、供应商属于核心经营数据，必须优先保障其完整性与可恢复性。

## 四、数据安全目标

### 4.1 总体目标

建立一套适合当前项目阶段的数据安全体系，使系统达到以下要求：

- 核心数据不依赖小程序本地缓存
- 核心数据以后端数据库为准
- 关键业务写入具备事务保护
- 关键变更有日志可追踪
- 数据具备备份与恢复能力
- 核心业务数据支持稳定导出

### 4.2 具体目标

1. 数据不易丢失
2. 数据变更可追溯
3. 关键业务一致性可保证
4. 故障后可恢复
5. 经营数据可导出

## 五、主要风险分析

### 5.1 数据丢失风险

可能来源包括：

- 后端仅使用临时内存存储
- 数据库未持久化
- 缺少自动备份
- 误删后无法恢复
- 部署或升级过程覆盖旧数据

### 5.2 数据不一致风险

可能来源包括：

- 采购单已保存但库存未增加
- 销售单已保存但库存未扣减
- 收款记录更新但订单状态未同步
- 多表更新过程中部分成功、部分失败

### 5.3 数据误操作风险

可能来源包括：

- 用户误删商品、客户、供应商
- 管理员误改价格或库存
- 非预期覆盖旧记录
- 缺少操作日志，无法回查责任和时间

### 5.4 导出风险

可能来源包括：

- 导出字段不统一
- 条件筛选不清楚
- 导出结果依赖前端拼装
- 导出数据缺少时间范围和业务上下文

## 六、设计原则

### 6.1 后端数据库为唯一可信数据源

小程序本地缓存仅作为临时展示或开发态回退能力，不能作为核心业务数据的最终来源。

### 6.2 核心业务写入必须事务化

凡是涉及订单、库存、收款、状态流转等多步骤修改的操作，都必须使用事务保证“要么全部成功，要么全部回滚”。

### 6.3 关键数据变更必须留痕

对商品、库存、订单、客户、供应商、用户等关键数据的新增、修改、状态变更、删除，应具备可审计能力。

### 6.4 备份恢复要可执行

备份方案不能只停留在文档层，至少要提供可操作的脚本、命令或流程说明。

### 6.5 导出能力应由后端统一提供

导出逻辑不应依赖前端自行拼接，应由后端统一定义筛选条件、字段顺序和输出格式。

## 七、核心设计方案

### 7.1 数据模型完善

建议数据库工作区优先审计并完善以下内容：

#### 7.1.1 主键规范

- 每张核心表必须有稳定主键
- 主键类型在项目内应保持一致
- 外部展示编号与内部主键应分离

例如：

- `id` 用于数据库内部关联
- `order_number` 用于业务展示

#### 7.1.2 约束完善

关键字段应补齐以下约束：

- 非空约束
- 唯一约束
- 必要默认值
- 合理长度限制

重点关注：

- 用户名
- 商品条码
- 采购单号
- 销售单号
- 状态字段
- 时间字段

#### 7.1.3 金额与数量字段规范

- 金额类字段应统一精度
- 库存数量字段应统一类型
- 避免金额使用浮点语义不清的字段设计

#### 7.1.4 时间字段规范

关键表建议统一包含：

- `create_time`
- `update_time`

必要时补充：

- `delete_time`
- `operate_time`
- `last_update_time`

### 7.2 事务一致性设计

以下业务必须重点检查事务边界：

#### 7.2.1 采购入库

流程包括：

- 采购单创建或更新
- 采购明细保存
- 库存增加
- 库存流水写入
- 采购状态更新

要求：

- 以上步骤必须在统一事务中执行
- 任一步失败必须整体回滚

#### 7.2.2 销售出库

流程包括：

- 销售单创建或更新
- 销售明细保存
- 库存扣减
- 库存流水写入
- 销售状态更新

要求：

- 防止销售单已保存但库存未扣减
- 防止库存扣减成功但订单状态未更新

#### 7.2.3 收款登记

流程包括：

- 更新订单已收金额
- 更新欠款金额
- 更新支付状态
- 必要时记录应收往来明细

要求：

- 收款金额、欠款金额、支付状态必须同步更新

### 7.3 删除策略设计

对关键业务数据，不建议默认做物理删除。

建议：

- 商品：优先逻辑删除或状态停用
- 客户：优先逻辑删除或状态停用
- 供应商：优先逻辑删除或状态停用
- 用户：优先停用而不是直接删除

物理删除仅适用于：

- 测试数据清理
- 明确无业务关联的数据
- 经管理员确认的特殊场景

### 7.4 审计与日志设计

建议保留并增强操作日志能力。

至少记录：

- 操作人 ID
- 模块名称
- 操作类型
- 目标对象 ID
- 目标对象摘要
- 操作说明
- 操作时间

重点记录场景：

- 登录 / 登出
- 商品新增、编辑、上下架、删除
- 库存调整
- 采购入库
- 销售出库
- 收款登记
- 用户状态变更

必要时可扩展数据变更前后对比能力，但本轮以“关键动作留痕”优先。

### 7.5 备份与恢复设计

#### 7.5.1 备份目标

确保在以下情况下仍可恢复核心数据：

- 数据库故障
- 误删误改
- 部署覆盖
- 服务器迁移

#### 7.5.2 备份策略

建议至少包含：

- 每日全量备份
- 重要环境保留多天历史版本
- 备份文件与运行目录分离
- 备份文件命名带时间戳

开发环境可先实现：

- 手工备份脚本
- 手工恢复脚本

后续再扩展：

- 定时备份任务
- 异地备份

#### 7.5.3 恢复策略

恢复流程至少应明确：

1. 停止写入
2. 选择备份版本
3. 恢复数据库
4. 校验核心表数据
5. 验证关键业务链路

#### 7.5.4 备份文件管理

建议记录：

- 备份时间
- 备份环境
- 备份说明
- 执行结果

### 7.6 数据导出设计

导出能力建议由后端统一支持，重点覆盖：

- 商品导出
- 客户导出
- 供应商导出
- 采购单导出
- 销售单导出
- 库存导出
- 操作日志导出

#### 7.6.1 导出规则

- 字段顺序固定
- 字段命名清晰
- 支持时间范围筛选
- 支持状态或关键字筛选
- 空值处理一致
- 导出逻辑不依赖前端拼装

#### 7.6.2 导出格式

本轮可先支持：

- JSON 结构化导出
- 文本摘要导出

后续可扩展：

- CSV
- Excel

## 八、建议落地任务拆分

### 工作包 A：数据库现状审计

输出：

- 当前表结构清单
- 当前实体清单
- 当前约束缺失清单
- 当前数据风险清单

### 工作包 B：核心表结构完善

输出：

- 修正后的核心表结构
- 必要索引与约束
- 实体字段对齐结果

### 工作包 C：关键事务保护

输出：

- 采购、销售、库存、收款事务边界说明
- 代码中的事务增强改动

### 工作包 D：日志与审计增强

输出：

- 操作日志增强方案
- 关键数据变更追踪范围

### 工作包 E：备份恢复方案

输出：

- 备份设计说明
- 恢复流程说明
- 可执行脚本或命令方案

### 工作包 F：导出能力建设

输出：

- 导出接口或服务设计
- 导出字段清单
- 导出示例结果

## 九、实施顺序建议

建议数据库工作区按以下顺序推进：

1. 先审计，不直接大改
2. 先补核心表和约束
3. 再补事务保护
4. 再补日志与审计
5. 再补备份恢复
6. 最后补导出能力

## 十、验收标准

本轮完成后，应达到以下标准：

- 核心业务数据以数据库为准
- 关键业务写入具备事务保护
- 核心表结构更稳定，约束更完整
- 重要操作可追踪
- 具备可执行的备份恢复方案
- 核心业务数据支持稳定导出

## 十一、交付物要求

数据库工作区最终至少应提交：

- 数据库现状审计说明
- 风险清单
- 表结构和实体修正方案
- 事务一致性改动说明
- 日志与审计方案
- 备份恢复方案
- 导出能力方案
- 剩余风险与下一步建议

## 十二、结论

当前项目的数据安全建设，应优先围绕“稳定存储、一致写入、变更留痕、可备份恢复、可稳定导出”五个方向推进。

对于当前阶段的项目体量，最务实的路径不是追求复杂架构，而是先把：

- 核心表结构
- 事务边界
- 操作日志
- 备份恢复
- 导出接口

这五部分做扎实。

只要这五项落地，系统的数据可靠性就会明显提升，也能为后续前端功能完善、报表建设和正式部署打下基础。
