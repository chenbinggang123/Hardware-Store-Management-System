# Agent MVP 开发计划

## 1. MVP 目标

在不破坏现有小程序业务页面的前提下，完成第一条可靠 Agent 闭环：

```text
自然语言销售需求
→ 客户和商品匹配
→ 查询历史价格和库存
→ 生成销售草稿
→ 用户确认
→ 创建正式销售单
```

## 2. 开发前置条件

以下问题会直接影响 Agent 安全性，应在正式写操作接入前完成或明确处理：

- 用户密码不能继续明文存储。
- 确认正式订单的用户身份必须可信。
- 核心业务数据需要明确 `tenant_id` 数据隔离方案。
- 销售创建和库存处理的事务边界必须明确。
- 正式写操作需要幂等键和版本校验。
- `target` 构建产物不应继续作为开发变更进入版本控制。

## 3. 开发阶段

### 阶段 0：设计评审

任务：

- 确认 MVP 只做销售开单，不含自动出库。
- 确认销售单草稿和正式订单的边界。
- 确认模型供应商和部署区域。
- 确认数据发送与保存策略。
- 确认测试店铺和真实用户访谈计划。

交付物：

- 已评审的产品流程。
- 工具清单和风险等级。
- 数据表评审记录。
- 首批评测语料。

### 阶段 1：业务底座整理

状态：进行中，已完成销售草稿、预览、版本校验和幂等提交的首版后端实现。

任务：

- 建立 Agent 专用查询 Service。
- 补充客户和商品标准搜索结果。
- 实现历史成交价查询。
- 明确库存唯一数据源。
- 增加销售草稿领域对象。
- 为正式销售单增加幂等创建入口。

验收：

- 不接模型也可以通过 API 完成草稿和确认流程。
- 相同幂等键不会创建重复订单。

当前已实现接口：

```text
POST /api/agent/sales-drafts
PUT  /api/agent/sales-drafts/{draftId}
GET  /api/agent/sales-drafts/{draftId}
POST /api/agent/sales-drafts/{draftId}/commit
```

当前实现中，确认销售草稿会创建正式销售单并更新客户欠款，但不会自动出库。

### 阶段 2：Harness 骨架

状态：进行中，已完成模型无关的有限 Agent Loop、只读工具注册、策略拦截、运行状态和工具 Trace 首版。

任务：

- 引入模型适配层。
- 建立 `AgentHarness` 和有限 Agent Loop。
- 实现 Tool Registry。
- 实现 Policy Engine。
- 实现 Run State 持久化。
- 实现 Trace 和结构化错误。

验收：

- 可以执行只读多工具调用。
- 达到步数、时间或重复调用限制后安全停止。
- 模型失败不会修改业务数据。

当前已注册只读工具：

```text
search_customers
search_products
check_inventory
```

当前已经提供默认关闭的 OpenAI-compatible 模型网关和只读对话接口：

```text
POST /api/agent/messages
```

启用配置：

```text
AGENT_MODEL_ENABLED=true
AGENT_MODEL_BASE_URL=https://模型服务地址/v1
AGENT_MODEL_API_KEY=模型服务密钥
AGENT_MODEL_NAME=模型名称
AGENT_MODEL_TIMEOUT_SECONDS=20
```

模型服务必须支持 Chat Completions 的 function tool calling 协议。未配置时，系统正常启动，但 Agent 对话接口返回“Agent 模型尚未启用”。Harness 已通过假模型网关完成循环测试；真实模型联调需在选定供应商和准备测试密钥后执行。

### 阶段 3：销售开单工具

任务：

- `search_customers`。
- `search_products`。
- `get_customer_last_prices`。
- `check_inventory`。
- `get_sales_draft`。
- `create_sales_draft`。
- `update_sales_draft`。
- `commit_sales_draft`。

当前已完成 `create_sales_draft` 与确认状态机的首版闭环。该工具属于 `R1_DRAFT`，模型请求调用时 Harness 只保存待执行参数并返回 `WAITING_APPROVAL`，不会立即创建草稿。

确认或拒绝接口：

```text
POST /api/agent/runs/{runId}/approval
```

请求示例：

```json
{
  "approved": true
}
```

小程序刷新页面或重新进入任务时，可以读取任务与结构化确认卡：

```text
GET /api/agent/runs/{runId}
```

当状态为 `WAITING_APPROVAL` 时，响应中的 `pendingAction` 包含 `toolName`、`risk`、标题、说明、结构化 `preview` 和过期时间。前端应直接渲染这些字段，不应从 `output` 文本中解析金额或业务状态。

确认操作同时校验登录操作人、任务状态和 30 分钟有效期。拒绝后任务进入 `CANCELLED`；超时进入 `EXPIRED`。确认成功后，Harness 会恢复暂停前的工具上下文，将真实草稿结果交回模型生成自然语言答复；如果模型总结失败，任务仍按业务成功处理，并明确提示“操作已成功执行”。创建草稿本身不会生成正式销售单。

正式订单提交工具 `commit_sales_draft` 已按 `R2_WRITE` 接入。执行前确认卡会重新读取草稿，展示客户、订单总额、已收金额、新增欠款、提交后欠款、商品明细和库存充足状态。草稿版本变化或库存不足时不允许进入确认。幂等键由 Harness 的 `runId` 和 `draftId` 确定性生成，模型不能提供或修改。提交只创建正式销售单并更新客户欠款，出库仍是独立业务动作。

销售草稿修改工具 `update_sales_draft` 已按 `R1_DRAFT` 接入。它采用完整替换而不是局部 Patch：模型必须传入草稿 ID、当前版本、客户、完整商品列表和已收金额。确认前系统只计算修改后的预览，不写数据库；确认后再次校验版本并更新。修改草稿不会创建正式订单、更新欠款或扣减库存。跨会话修改前可使用只读工具 `get_sales_draft` 获取完整草稿及当前版本。

验收：

- 工具不能跨租户访问数据。
- 多候选时必须暂停。
- 未确认时不能创建正式订单。
- 重复确认不重复执行。

### 阶段 4：小程序 Agent 页面

任务：

- Agent 首页入口。
- 消息列表。
- 建议问题。
- 候选选择卡片。
- 销售草稿卡片。
- 确认、修改和取消。
- 最近任务和断线恢复。
- 跳转传统销售表单。

验收：

- 用户能识别查询、草稿和正式结果。
- 页面刷新后可以恢复待确认任务。
- Agent 不可用时可以转传统开单页。

### 阶段 5：评测与灰度

任务：

- 建立不少于 100 条真实表达评测集。
- 覆盖同名客户、相似商品、缺价格和库存不足。
- 记录模型与工具 Trace。
- 小范围真实用户测试。
- 根据错误类型调整工具和产品流程。

上线门槛：

- 高风险动作绕过确认率为 0。
- 重复确认导致重复订单率为 0。
- 跨租户数据访问测试全部通过。
- 商品和客户歧义场景能够正确暂停。
- 工具失败时不会错误提示成功。

## 4. 测试矩阵

| 场景 | 预期行为 |
| --- | --- |
| 唯一客户、唯一商品 | 自动生成草稿 |
| 多个同名客户 | 显示候选并暂停 |
| 多个相似商品 | 显示规格和库存候选 |
| 用户未说数量 | 追问数量 |
| 用户说“还是以前价格”但无历史订单 | 追问价格策略 |
| 库存不足 | 显示库存并禁止静默继续 |
| 用户修改数量 | 更新同一草稿版本 |
| 用户拒绝确认 | 不创建订单 |
| 用户重复点击确认 | 返回第一次执行结果 |
| 模型超时 | 不产生正式业务数据 |
| 工具执行后响应丢失 | 根据幂等键查询原结果 |
| 非当前店铺数据 | 拒绝访问 |

## 5. 首批评测语料结构

每条样本包含：

```json
{
  "input": "给老王开两个东成电钻，还是以前价格，先记账",
  "expectedIntent": "CREATE_SALES_DRAFT",
  "expectedTools": [
    "search_customers",
    "search_products",
    "get_customer_last_prices",
    "check_inventory",
    "create_sales_draft"
  ],
  "mustAsk": [],
  "mustNotExecute": [
    "commit_sales_order"
  ],
  "expectedRisk": "R1"
}
```

## 6. 建议开发顺序

```text
先做无模型的草稿与确认 API
→ 再做只读工具
→ 再接 Agent Loop
→ 再接正式订单确认
→ 最后做小程序语音和个性化记忆
```

这个顺序保证即使模型效果暂时不理想，核心业务底座仍然可测试、可复用。

## 7. 待确认事项

- MVP 是否允许创建正式销售单，还是只生成草稿并跳转传统表单。
- 正式销售单创建后是否立即影响客户欠款。
- 出库是否永远作为独立动作。
- 商品库存以 `product.stock` 还是 `inventory.quantity` 为唯一数据源。
- 首期模型服务商与数据驻留要求。
- 是否从第一期开始引入多租户字段。
- 测试用户能否提供真实但脱敏的口语开单样本。

## 8. MVP 完成定义

只有同时满足以下条件，才视为 MVP 完成：

- 一条自然语言销售任务可以走完整闭环。
- 所有正式写操作可追踪、可幂等、可确认。
- Agent 失败不破坏已有业务数据。
- 用户可以修改、拒绝或离开 Agent 流程。
- 关键自然语言测试具备可重复的自动评测。
- 原有销售页面仍能独立完成相同业务。
