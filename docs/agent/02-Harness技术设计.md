# Agent Harness 技术设计

## 1. 设计目标

Harness 是模型外围的可信控制平面，负责：

- 有限 Agent Loop。
- 上下文构建。
- 工具注册与路由。
- 参数、权限和风险校验。
- 人工确认。
- 运行暂停与恢复。
- 幂等和重复调用保护。
- 日志、Trace 和评测数据采集。

模型不拥有数据库、Repository、任意网络、文件系统或 Shell 权限。

## 2. 总体架构

```text
微信小程序
    ↓
AgentController
    ↓
AgentHarness
    ├─ ContextBuilder
    ├─ ModelGateway
    ├─ AgentLoop
    ├─ ToolRegistry
    ├─ PolicyEngine
    ├─ ApprovalManager
    ├─ RunStateStore
    ├─ MemoryManager
    └─ TraceRecorder
    ↓
AgentTool
    ↓
现有 Service
    ↓
Repository / MySQL
```

## 3. 技术决策

### 3.1 首期方案

- 保留现有 Spring Boot 应用。
- 使用 Spring AI 作为模型和工具调用适配层。
- Harness 的循环、策略、审批和状态由项目自己实现。
- 模型通过 `AgentModelGateway` 抽象，避免业务代码绑定单一供应商。
- 首期只实现一个经营 Agent。
- 首期不启用通用代码执行沙箱。

### 3.2 决策理由

- 可以复用现有 Service、事务和认证体系。
- Agent 的业务安全边界必须由本项目掌控。
- 国内模型、海外模型和本地模型需要具备替换空间。
- 销售开单是强顺序、共享状态任务，多 Agent 不会提高可靠性。

## 4. Agent Loop

### 4.1 双层循环

内层循环在单个请求内执行低风险工具：

```text
模型 → 查询工具 → 工具结果 → 模型 → 下一工具或最终回复
```

外层循环负责跨请求暂停和恢复：

```text
运行 → 需要用户输入/确认 → 保存状态 → 返回小程序
→ 用户操作 → 恢复原运行 → 继续执行
```

### 4.2 终止条件

- 模型返回最终结果。
- 缺少必要信息。
- 遇到需要人工确认的工具。
- 达到最大模型调用次数。
- 达到最大工具调用次数。
- 检测到相同调用循环。
- 达到超时或成本上限。
- 工具返回不可恢复错误。

### 4.3 初始限制

| 项目 | 建议值 |
| --- | --- |
| 单轮最大模型调用 | 6 |
| 单轮最大工具调用 | 10 |
| 相同工具和参数调用 | 1 次 |
| 单轮总超时 | 20 秒 |
| 单次确认允许写操作 | 1 个 |
| Run 默认有效期 | 30 分钟 |
| Action 默认有效期 | 10 分钟 |

## 5. 运行状态

```text
CREATED
→ RUNNING
   ├─→ WAITING_USER_INPUT
   ├─→ WAITING_APPROVAL
   ├─→ COMPLETED
   ├─→ REJECTED
   ├─→ FAILED
   ├─→ CANCELLED
   └─→ EXPIRED
```

恢复时必须使用原 `runId`，并校验状态和版本，不能把“确认”当成一条无关联的新对话。

## 6. 工具设计

### 6.1 工具元数据

每个工具必须声明：

- 名称和业务说明。
- 输入和输出 Schema。
- 风险等级。
- 所需权限。
- 是否需要确认。
- 是否幂等。
- 是否可逆。
- 超时与重试策略。

### 6.2 风险等级

| 等级 | 示例 | 执行规则 |
| --- | --- | --- |
| R0 | 查询商品、客户、库存 | 可自动执行 |
| R1 | 计算报价、创建草稿 | 自动执行并展示 |
| R2 | 创建正式订单、修改资料 | 用户确认 |
| R3 | 出入库、收款、退款 | 强化确认并重新校验 |
| R4 | 删除、恢复、批量高风险操作 | 管理员认证或禁止 Agent 执行 |

### 6.3 MVP 工具

```text
search_customers
search_products
get_customer_last_prices
check_inventory
create_sales_draft
update_sales_draft
preview_sales_order
commit_sales_order
```

正式出库不纳入首个闭环，作为后续独立确认动作设计。

## 7. 策略引擎

工具执行前必须依次完成：

```text
工具白名单
→ 参数 Schema
→ tenantId 强制注入
→ 用户身份
→ 角色权限
→ 业务范围
→ 风险等级
→ 确认策略
→ 幂等检查
→ 业务状态校验
```

`tenantId`、`userId` 和权限不能由模型参数提供，必须由认证上下文注入。

## 8. 两阶段写入

副作用操作统一使用：

```text
prepare/preview
→ 保存 AgentAction
→ 用户确认
→ commit
```

确认执行时必须重新检查：

- 操作未执行且未过期。
- 确认人为合法用户。
- 草稿版本未变化。
- 订单和库存版本未变化。
- 参数仍满足业务规则。
- 幂等键未被消费。

## 9. 上下文与记忆

### 9.1 本轮上下文

- Agent 固定规则。
- 当前用户、店铺和权限摘要。
- 当前任务状态。
- 最近相关消息。
- 已确认实体。
- 当前草稿。
- 可用工具。
- 最近工具结果。

只提供完成当前任务所需的最小数据。

### 9.2 长期记忆

长期记忆采用结构化存储：

- 商品别名。
- 客户称呼。
- 客户价格策略。
- 默认付款方式。
- 确认偏好。

模型只能提出记忆建议，不能未经策略判断直接写入长期记忆。

## 10. 失败与降级

| 故障 | 处理方式 |
| --- | --- |
| 模型超时 | 不执行写操作，允许重试或转传统页面 |
| 工具超时 | 查询实际业务状态后再决定是否重试 |
| 参数非法 | 将结构化错误返回模型修正一次 |
| 商品无法唯一匹配 | 返回候选卡片 |
| 审批超时 | Action 标记为 EXPIRED |
| 重复确认 | 返回原执行结果，不再次执行 |
| Agent 服务不可用 | 保留原有页面和接口 |

## 11. 可观测性

每个 Run 应记录：

- 用户原始输入。
- 使用的模型和版本。
- 上下文版本，不记录不必要的敏感原文。
- 模型耗时和 Token。
- 工具名、参数摘要、结果摘要和耗时。
- 策略决定。
- 审批人和审批时间。
- 最终结果和错误类型。

生产日志不得写入密码、完整 Token、银行账号等敏感信息。

## 12. 包结构建议

```text
com.example.demo.agent
├─ api
├─ harness
├─ model
├─ tool
├─ policy
├─ approval
├─ memory
├─ trace
└─ persistence
```

Agent Tool 只调用 Service，禁止直接注入 Repository。
