# ADR-0005：Harness 保持最小循环并拆分审批与上下文

- 状态：已采用
- 日期：2026-10-01

## 背景

工具执行管线拆出后，`AgentHarness` 仍然直接处理会话历史、JSON 编解码、审批状态字段、过期和取消分支，以及确认卡片标题。增加新业务工具虽然不再影响执行代码，但仍可能迫使开发者修改 Harness 的基础状态逻辑。

## 决策

将 Harness 收敛为有限模型循环和组件编排，并建立三个稳定边界：

- `AgentContextManager`：会话上下文、工具结果持久化格式和重复调用指纹。
- `AgentApprovalService`：审批暂停、原子抢占、过期、取消、恢复与失败收口。
- `AgentRunResultFactory`：API 结果和结构化确认卡片。

Harness 只保留以下职责：

1. 校验一次运行的入口参数。
2. 控制模型步数与工具调用总量。
3. 检测同一运行中的重复工具调用。
4. 把模型、工具执行、审批和运行状态组件串联起来。
5. 在模型循环级异常时结束运行。

## 状态约束

- 会话必须先成功解析，再创建运行记录，避免孤立 Run。
- 审批只能从 `WAITING_APPROVAL` 原子抢占为 `RUNNING`。
- 抢占后的任何准备或执行异常都必须落入明确终态，不能遗留不可恢复的 `RUNNING`。
- 取消和终态失败必须清空待确认工具字段。
- 确认卡片由统一工厂创建，标题等展示信息由 `AgentToolDefinition` 声明，业务工具不得在 Harness 或结果工厂中增加按工具名判断的分支。

## 结果

新增商品、采购、Excel 和订单能力时，通常只需要新增工具、服务及对应的结果展示元数据；不需要修改模型循环、上下文恢复格式或审批并发控制。代价是组件数量增加，因此要求每个状态边界拥有独立单元测试，并由全量回归验证组合行为。
